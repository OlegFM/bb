5. Concern: dev-session PID tracking goes stale almost immediately
   on Windows (packages/scripts/src/lib/dev-app-launcher.ts,
   Task 8a/8b scope, not modified by this task)
================================================================
Reproduced 3 times (once via Git Bash, twice via native PowerShell),
consistently:

1. `pnpm dev:app current` (or the dev-server phase of `dev:desktop`)
   starts the dev server, writes the pid file
   (~/.bb-dev/<instance>/dev-supervisors/dev-app-dev.pid), waits for
   "Host daemon started", and its own final status print correctly
   shows "Dev session: running".
2. The underlying `pnpm run dev` process tree (Vite, @bb/server,
   @bb/host-daemon, managed by scripts/dev-supervisor.mjs with its own
   auto-restart) keeps running and serving traffic indefinitely --
   confirmed via `Invoke-WebRequest .../health` returning 200 minutes
   later, after closing the window that started it, and even after the
   individual server/host-daemon PIDs were taskkill'd (the supervisor
   spawned replacements automatically).
3. Within seconds of `pnpm dev:app current` (or `dev:desktop`)
   returning, a *separate* `pnpm dev:status` invocation already
   reports "Dev session: stopped": the PID recorded in
   dev-app-dev.pid has already exited (`tasklist` shows no such
   process), even though the actual dev server, vite and host daemon
   remain alive under different, untracked PIDs.
4. As a direct consequence, `pnpm dev:stop` cannot find a live PID to
   stop and reports "not running" while real listeners remain on all
   three instance ports (23813, 31813, 15813) -- confirmed repeatedly.

Likely root cause (not fixed, out of this task's five-file scope):
`startLoggedProcess` in packages/scripts/src/lib/dev-app-launcher.ts
spawns with `detached: request.platform !== "win32"`, i.e.
`detached: false` on Windows. Node's child_process docs recommend
`detached: true` (CREATE_NEW_PROCESS_GROUP) specifically on Windows so
a spawned child survives the parent's console/process lifecycle;
`false` leaves the immediate "pnpm run dev" child tied to a console
session that goes away once the short-lived run-dev-app.ts process
exits, while grandchild processes (server/host-daemon, which use their
own detached spawns inside scripts/dev-supervisor.mjs) survive
independently and re-parent themselves as untracked orphans.

Net effect: the dev server itself is fully usable and durable on
Windows (satisfying the spirit of observations 2 and 3 below), but
`pnpm dev:status` / `pnpm dev:stop`'s PID-file bookkeeping is
unreliable within seconds of every "current"/"desktop" run. This is a
Task 8a/8b (dev-app-launcher.ts / pid-file.ts) concern; it is reported
here rather than patched, since this task's commit is scoped to five
specific files and packages/scripts/src/lib/dev-app-launcher.ts is not
one of them.

9. After the session-host fix (fix round 1)
================================================================
Root cause confirmed: on Windows, libuv assigns every non-detached
spawned child to a kill-on-close job object (with silent breakaway for
grandchildren), so the previous `detached: request.platform !== "win32"`
branch (false on win32) tied the tracked "pnpm run dev" process to a
console/job that went away once the short-lived run-dev-app.ts process
exited, while its grandchildren (server/host-daemon/vite, which
self-detach inside scripts/dev-supervisor.mjs) survived as untracked
orphans.

Fix: on win32, `startLoggedProcess` now spawns a small, `detached: true`,
`windowsHide: true` Node "session host" (packages/scripts/src/commands
/run-dev-app-session-host.ts, run via the same `node --conditions=source
--import tsx` / `node dist/...` invocation as the caller) whose own child
(the real dev-server or desktop command) is spawned NOT detached, with
stdio piped into the log file. The host survives the launcher exiting;
its own child sits inside the host's job and dies with it, so
`taskkill /PID <host> /T /F` now tears down host + child (and any
console/conhost it created) together. POSIX now always passes
`detached: true` too (previously conditional), unchanged in effect since
POSIX already relied on detached process groups for stop/signal delivery.

Debugging note: the first attempt at the fix used the *target child's*
`cwd` as the session host's own spawn cwd (as directed). This broke the
`dev-app-launcher.test.ts` "tracked processes" tests, whose `cwd` is a
bare `mkdtempSync` temp directory: `node --conditions=source --import tsx
<script>` fails to resolve the `tsx` loader package when launched from a
directory with no `node_modules` in its ancestry (confirmed directly:
`cd <tempdir-with-no-node_modules> && node --conditions=source --import
tsx -e "..."` throws `ERR_MODULE_NOT_FOUND: Cannot find package 'tsx'`),
so the host process died within ~1s without ever writing the log, and
`pnpm exec turbo run test -- dev-app-launcher` hung until the vitest test
timeout. Root repo cwd (`C:\Users\olege\Work\bb`) always has `tsx`
resolvable, so this never affects production usage (`run-dev-app.ts`
always passes `cwd: repoRoot`); only the unit tests' synthetic temp `cwd`
triggered it. Fixed by pointing the two affected tests' `startLoggedProcess`
calls at the real repo root (`monorepoRoot`, resolved from the test file's
own location) instead of the scratch temp directory -- the target
`node -e` child doesn't care what directory it runs in, it only needed a
directory where `tsx` resolves for the host process spawned from it.
